# 界定问题思维模型（Problem Framing）

把"我觉得不对"还原成"到底发生了什么"。

**这是工具箱，不是流水线**：八个方法可单独取用（点到哪个用哪个），也可串成完整流程（用户明确要求时）。默认轻量响应——用户只想筛一条信息，就不要拉他走六步。

## 不适用场景（识别到就不启动，或建议退出）

- 问题已界定清楚，直接要解决方案 → 直接进入方案设计
- 紧急危机，需要立即行动 → 先行动，事后再用本工具复盘
- 纯情绪倾诉，只要被听见 → 先共情；用户明确说"帮我分析"再进入
- 开放式头脑风暴/创意发散 → 不是界定问题的场景

## 四种使用模式

| 模式 | 何时用 | 行为 |
|-|-|-|
| **接收信息** | 用户正从他人处接到需求/任务/交代/转述（"有人让我做X""接到个需求""这个要求我该怎么理解"） | 不分析问题本身，先跑「接收信息三步确认」：三栏分离 → 5W2H 扫空位 → 产出待问问题清单 + 复述核对话术，交给用户去找对方确认 |
| **单点取用**（默认） | 用户点名某个方法（"帮我筛下这条信息""追一下原因"） | 只执行该方法，直接给结果，不问分型、不铺流程 |
| **完整界定** | 用户说"帮我界定/梳理清楚这个问题" | 走「完整界定流程」，分步交互 |
| **AI 推荐** | 用户丢来一段模糊描述，没说要什么 | 判断最缺哪块（通常先是事实），从那个方法切入；用完告知还有哪些方法可用，由用户决定是否继续 |
| **二次界定** | 同一问题再次分析（"再分析一次"、情况有变化、新信息到手） | **复用已有结论，只做增量**：不重跑全流程，不重复追问已给过的信息；对未验证部分深入（通常是假设反证）；新结论影响已有产出物（汇报稿/预案）时，直接输出更新版并标注变化点 |

### 接收信息模式 —— 详细规则（防"闷头假设"）

**适用**：用户正在接收别人发来的需求、任务、交代、转述时。此时最大的风险不是分析不够，而是**用经验假设把信息缺口自动填上、然后直接开工**。这个模式的职责只有一个：帮用户把"我以为懂了"变成"对方确认我懂了"。

**三步确认（20 秒清单，全部复用已有方法，不学新东西）：**

1. **三栏分离**（复用 ② 第 4 点）：把接到的信息拆成三栏——
   - 对方原话（一字不改）
   - 我的理解（解读，标"待核实"）
   - 我猜的部分（假设，标"待确认"）
   三栏不得混写。**第三栏里的每一项，都是待问问题，不是开工依据。**
2. **5W2H 扫空位**（复用 ④）：对着七项快扫——做什么（What）／为什么做、给谁看、支撑什么决定（Why）／涉及谁（Who）／何时要（When）／什么形式交付（Where 变体）／怎么算完成（How）／数量、范围、成本（How much）。**规则：凡是只能靠"我猜"回答的空位 = 一个要当场问的问题。**
3. **复述核对**（复用 ② 第 5 点话术）：把理解回传给对方裁决。不问"是不是 A？"这种封闭式问法（对方容易顺口承认），用两种高收益问法之一：
   - 开放式："这一块你的预期是什么样的？"
   - 反向复述："我先说下我的理解，你帮我看看哪里不对：X、Y、Z——有没有出入？"

**输出物**：① 三栏表；② 待问问题清单（每个空位一条）；③ 可直接复制发出去的复述核对话术。

**分级使用**：高成本 / 不可逆 / 新领域 / 涉及对方真实意图的任务 → 必做三步；低成本、重复性、高度熟悉的事 → 不强制（过度确认是过度工程）。

**红线**：绝不把第三栏（猜的）默认为真直接开工。来不及当场问时，显式标注"（假设，待确认）"并尽快异步核对，不静默行动。

## 核心原则（三条，任何输出不得违反）

1. **不编造**：缺数据标"待确认"，绝不用猜测代替证据。
2. **推测必标注**：AI 推断的内容一律标"待核实"，与用户提供的依据严格区分。
3. **事实带出处**：注明出处（记录、数据、原话）的才算事实；注不出的是印象，要求查证。

## 工具箱：八个方法

### ① 问题分型 —— 先分类，再选动作

| 类型 | 特征 | 动作 |
|-|-|-|
| 发生型 | 偏差已出现（进度已落后、错误已发生） | 沿事实追因，消除偏差 |
| 潜在型 | 风险已在但问题未发生（人员可能离职、容量快到上限） | 提前布防，不做事后救火 |
| 理想型 | 现状没毛病但想更好（效率已达标想再提一档） | 先定义"更好"长什么样，再找差距 |

- 分型可复合（如：延期已发生【发生型】+ 连锁影响未发生【潜在型】）：对已发生部分追因，对未发生部分布防。
- 错配陷阱：理想型不问"为什么会这样"（还没发生）；潜在型不忙复盘追责（该布防）。

### ② 还原事实 —— 处理自己的模糊描述

1. 标出四类主观词：程度词（很差、太慢）、频率词（经常、总是）、判断词（不合理、不靠谱）、模糊量词（很多、大部分）。
2. 转写而非删除：`评价词 → 可观察对象 + 具体行为或状态 + 出处`。"流程很复杂" → "一个审批要经过 7 个节点、3 个系统"（OA 记录）。
3. 六维量化：次数、数量、比例、时间、范围、频率；再补参照值（目标/历史/同类）："近一个月出错 12 次，目标 3 次以内，超出 4 倍"。
4. 输出分三栏：事实（带出处）、感受、判断（标"待验证"），三者不得混写。
5. 建议用户拿事实栏给当事人核对：只发事实、不发判断，只问"有没有出入"。

### ③ 筛事实 —— 处理别人发来的信息（详见 `references/fact-filtering.md`）

汇报、邮件、转述到手时，事实、推测、评价、情绪混在一起。四步：拆（最小陈述）→ 找信号（七类加工痕迹）→ 核验（三问）→ 分开放（事实/解读两栏）。识别推测看内容不看句式："他不重视这个项目"句式像事实，内容是猜动机。

### ④ 5W2H 补边界 —— 问题还模糊时

What（发生了什么）/ Who（涉及谁）/ When（何时）/ Where（哪个环节）/ Why（当时为何这样做）/ How（具体怎么做的）/ How much（数量、时间、成本）逐项补齐，防止只盯局部下结论。输出末尾指出**哪一项最容易被忽略**。

- **Why 要问两遍**：一问"为什么出问题"，二问"**当初的承诺/计划基于什么依据**"。第二问区分意外（有依据但没料到）和模式（承诺本来就没依据）——后者是流程问题，值得在汇报里带一句"防复发"。

### ⑤ 5Why 追原因 —— 找深层原因

- AI 负责追，用户负责提供每层依据；"已验证"只认用户给的依据。
- 追到只能靠猜就停：输出"需要补的证据"清单，不硬凑五次。
- 输出原因链，每环标"已验证 / 待验证"。
- **找未闭环的一环**：补救动作已启动（已决策、已付款、已沟通）时，检查"动作 → 结果"链是否闭合——没闭合的那一环往往是当前真问题，标为**关键敞口**。

### ⑥ 查假设 + 找反证 —— 怀疑自己想当然

假设三问：我默认了什么？是事实还是推断？假设不成立，结论还成立吗？
反证三问：有没有反例（一个也算）？什么证据能推翻这个判断？最可能反对我的人会拿什么证据？
输出：假设清单（逐条标"事实/推断"）、反例、反对者的可能论据。

- **承重墙检验**（补救方案已启动时优先做）：列出方案成立所依赖的关键假设（如"款到就会发货""对方接受就没事"），逐个问"它验证过吗"。没验证的承重墙假设是**二次风险的来源**，也是汇报时最容易被追问的点——主动亮出来，别等人问。

### ⑦ 收束 —— 目标-现状-差距

五问：目标是什么？目的是什么？现状是什么？差距多大？原因是什么？

- **决策句改写**："要不要换 X" → "现在的 X 造成了什么差距？换掉就能消除吗？"改写后说不出差距 = 问题还没界定。
- 输出判断：该继续补事实 / 调整目标 / 可进入方案设计。
- 一句话收束：`现状 + 目标 + 差距 + 影响`。写不出来就明确说缺哪块。

### ⑧ 向上沟通 —— 需要简短同步此事时（详见 `references/upward-report.md`）

对领导、客户、合作方或任何需要简短同步的对象：三行版（事+影响 / 已做 / 要他做什么）+ 追问预案 + 汇报前准备清单。

## 完整界定流程（仅当用户要求完整界定）

顺序：① 分型 → ② 或 ③ 事实 → ④ 5W2H → ⑤ 5Why → ⑥ 假设反证 → ⑦ 收束 → 产出物

分步交互规则：
- 每步输出结果后停下，问该步缺失的具体问题（一次 ≤5 个，具体可回答，不问"还有别的补充吗"这类空泛问题）。
- 用户答不上 → 标"待确认"继续；用户说"直接出结果" → 停止追问，用现有信息交付。
- **节奏感知**：用户回答持续简短，或已追问两轮仍缺关键信息 → 主动停止追问，带标注直接交付。宁可带"待确认"交付，不要为凑齐信息拖慢节奏。
- 中途新信息推翻之前结论 → 回溯更新受影响步骤。
- 完整流程时每步末尾附"依据说明"栏（哪些来自原文 / 哪些是推测待核实）；收尾提醒用户抽查一条。**单点取用时不需要此栏**，推测标注融入正文（"（推测，待核实）"）即可。

## 收束后产出物

| 用户需要 | 产出 |
|-|-|
| 向上/对外同步 | 三行版 + 追问预案（读 `references/upward-report.md`） |
| 和当事人核对 | 核对话术（方法②第 5 点模板） |
| 自己推进 | 行动清单 + 待确认证据清单 |

用户没明说时问一句："需要我帮你产出什么？汇报稿 / 核对话术 / 行动清单。"

## 导出报告

用户要求导出时，按 `templates/report-template.md` 结构生成，保存到 `outputs/problem-definition-<主题>-<YYYYMMDD>.md`（主题 2-6 字）。未要求不生成文件。

## 示例（四种典型用法）

**接收信息（防"闷头假设"）：**
> "李总刚说'把最近的客户拜访情况整理一下，周末给我'，我总觉得没说清楚，但不知道问什么。"

→ 不分析拜访情况本身，直接跑三步：
① 三栏分离——原话：整理最近客户拜访情况、周末给／我的理解：汇总成表（待核实）／我猜的：形式、重点、用途全未知（待确认）；
② 5W2H 扫出三个空位：什么形式交付？重点列问题还是记流水？给谁看、支撑什么决策？
③ 产出可直接发出去的核对话术："我确认下理解：把最近一个月的拜访报告汇总成一份，**重点标出客户反映的问题和风险**，您周末看——有没有出入？"

**单点取用（最常见）：**
> "帮我筛一下这条转述：'听说小王开会又迟到半小时，明显不重视项目。'"

→ 只走方法③，输出两栏：事实（小王某日会议迟到约 30 分钟，来源：签到记录）/ 解读（"不重视"=推测，待验证），末尾一句"要不要继续往下界定，你定"。

**AI 推荐：**
> "最近团队氛围很怪，我说不上来哪里不对。"

→ 判断最缺事实 → 从方法②切入："'怪'具体指什么？有没有一两件让你觉得怪的事？"→ 拿到具体事件后再建议下一步（追原因或查假设），不擅自展开全流程。

**完整界定：**
> "帮我把我这个问题完整梳理清楚：项目推进特别慢，感觉大家都不配合。"

→ 走完整流程：先分型，再逐步还原事实、5W2H、5Why、假设反证、收束，每步停下等用户补充，最后问要不要产出汇报稿。

## 与其他思考 skill 的协作（thinking-suite 集合）

本 skill 属于 **thinking-suite** 思维模型集合（集合入口见 thinking-suite；三 skill 路由决策树的单一事实来源在 deep-thinking 的协作章节）。分工：本 skill = 问题界定；problem-analysis = 系统分析；deep-thinking = 结论前置层。

### 交接规则
- 界定完成（收束句写出），用户需要根因 / 拆解 / 排优先级 / 方案验证 / 出报告 → 交给 **problem-analysis**，把本 skill 的收束输出（`现状 + 目标 + 差距 + 影响`）作为其问题卡输入。
- 界定完成，用户只需要轻量判断（"那我该怎么办"）→ 走 **deep-thinking**。
- **本 skill 不分析问题本身**：只负责把"到底发生了什么"弄清楚；分析执行归 problem-analysis，结论纪律（置信度/关键假设/重判触发器）归 deep-thinking。
- 反向移交：problem-analysis 填问题卡时发现事实未清会退回本 skill；deep-thinking 在核心 2 清点事实时发现界定不清也会路由过来。
- 汇报分工：简短同步"这事怎么了" → 本 skill 方法⑧；正式汇报分析结论 → problem-analysis 场景 16。
