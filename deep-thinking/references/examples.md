# 深度思考技能 - 示例集

本文件是 `deep-thinking` skill 的示例库，供 agent 在执行流程时按需参考。SKILL.md 只保留骨架速览，详细示例集中在此。

## 示例 1：完整模式

**用户**："我们创业团队该不该现在拿这笔投资？条款有点苛刻。"

**判断**：重大、不可逆、有对立面 → 走完整模式，启用全部可选步。

- **重构问题**：不是"该不该拿"，而是"在当前现金流和估值预期下，苛刻条款的代价是否低于不拿钱的死亡风险"。
- **已知/未知**：事实=条款细节、当前跑道；推断=投资方看出我们急；假设=下一轮能拿到更好条款；缺口=投资方未来是否追加。
- **拆解**（生存视角 / 博弈视角）：生存视角=不拿的破产概率 vs 条款代价；博弈视角=投资方给苛刻条款是因为看出我们急还是看出我们弱？
- **Steelman 反方**：反方（不拿）会说——苛刻条款伴随控制权丧失，未来融资被锁死，宁可缩减规模慢一点。自检最脆弱点=我对"下一轮能拿到更好条款"的假设。
- **二阶后果**：拿了→控制权稀释→后续议价权下降→可能被踢出方向决策；不拿→缩减规模→关键人才流失→产品进度落后→还是得拿更差条款。
- **Pre-mortem**：若一年后证明错了，最可能因为=① 高估下一轮估值 ② 低估某条隐蔽条款的杀伤力 ③ 团队没扛住缩减期。
- **结论**：倾向拿，有条件——[高把握] 不拿的死亡风险大于条款代价；[中把握] 条款里 X 条可谈判；[低把握] 下一轮能更好。关键假设=现金流测算准确。重判触发器=若 X 条无法修改且涉及控制权，则改为不拿并缩减。

## 示例 2：精简模式

**用户**："你怎么看现在学 Rust 还值不值？"

**判断**：中等复杂度，用户要判断不要长篇 → 走精简模式，启用可选 A（多框架）。

- **结论**：[高把握] 值得学，但不该作为"下一个要学的语言"首选，除非方向是系统/性能/基础设施；[中把握] 对多数业务后端开发者，投入产出比不如把已用语言和工程能力做深。
- **关键假设**：你目前方向是业务后端而非系统编程；"值"按职业投入产出比定义。
- **重判触发器**：若目标岗位明确要求 Rust，或打算转系统/基础设施方向，则改为"优先学"。
- （简注：重构"值不值"=按方向算投入产出比；用"方向匹配度"和"机会成本"两个框架对比；反方=已有语言做深可能回报更高。）

## 示例 3：主动提议

**用户**："最近团队士气有点低，几个人提了离职。"

**判断**：用户抛现象不提问，但隐含"这意味着什么 / 我该怎么办"的判断需求。未命中显式触发短语，但值得深想。

**agent 主动问**："这个问题值得深想一下，要不要我走深度思考流程？可能涉及是真士气问题还是个别现象、根因在哪、该不该现在干预。"

- 用户同意 → 走流程。
- 用户拒绝 → 正常给几句观察建议，不强推。

## 示例 4：显式唤起（强制触发）

**用户**："深度思考一下，我们该不该把后端从 Node 换成 Go。"

**判断**：用户用了显式命令 → 无论问题复杂度如何，走完核心 3 步并给带置信度的结论。

- **重构问题**：不是"换不换"，而是"换的语言收益是否大于迁移成本 + 团队学习成本 + 业务中断风险"。
- **已知/未知**：事实=当前痛点、团队规模；假设=Go 能解决 X 痛点；缺口=团队对 Go 的接受度、迁移期业务影响。
- **结论**：[高把握] 若当前痛点是性能/并发且团队稳定，值得评估；[中把握] 若痛点是工程规范问题，换语言治标不治本；[低把握] 迁移后团队能否快速上手。关键假设=痛点真因是语言而非架构/规范。重判触发器=若痛点根因在架构或规范，则改为"不换语言，先治架构"。
